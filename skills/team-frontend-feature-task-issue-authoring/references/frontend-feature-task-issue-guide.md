# 프론트엔드 기능·테스크 이슈 가이드

## 적용 범위

`[FE][FEATURE]`는 프론트엔드가 제공할 사용자 결과를 합의하는 부모 이슈다. `[FE][TASK]`는 그 부모의 범위가 독립적으로 배정·구현·리뷰 가능한 작업일 때만 만드는 하위 이슈다. 화면, 사용자 흐름, 컴포넌트, 클라이언트 상태, 입력 검증, 접근성, 반응형 UI, API 연동, 프론트엔드 테스트·문서가 대상이다.

도메인 규칙, 데이터 스키마, 인증 정책처럼 백엔드가 소유하는 구현은 `[BE][FEATURE]` 또는 `[BE][TASK]`로 분리한다. API 계약 협의와 의존성은 관련된 양쪽 이슈에 명시한다.

## 테스크 이슈를 만들기 전 판정

`[FE][FEATURE]`의 본문에 화면·상태·API·테스트 항목이 있다고 해서 각각 테스크 이슈를 만들지 않는다. 아래 중 하나 이상이 성립할 때만 `[FE][TASK]`로 분리한다.

- 서로 다른 화면 또는 사용자 흐름이 독립 PR·담당자·릴리스·Feature Flag로 관리되어야 한다.
- 공통 상태·API 연동·디자인 시스템 변경이 여러 화면에 영향을 주어 별도 리뷰와 회귀 검증이 필요하다.
- E2E, 접근성, 시각 회귀, 다중 브라우저·디바이스 검증이 별도 환경, 담당자 또는 일정으로 수행되어 독립 증빙이 필요하다.
- API 계약 확정, 디자인 확정, 백엔드 기능 부모 완료처럼 명확한 선행·후행 관계가 있다.
- 한 이슈의 변경량이 하나의 PR·리뷰·롤백 단위로 다루기 어렵다.

다음은 분리하지 않고 기능 부모 또는 같은 구현 테스크의 완료 조건으로 남긴다.

- 화면 구현과 함께 작성하는 컴포넌트 단위 테스트, 로딩·오류 상태, 간단한 스타일 수정
- 같은 담당자가 하나의 PR에서 함께 바꾸는 페이지·컴포넌트·로컬 상태
- 디자인 또는 API 계약이 아직 확정되지 않아 독립 결과를 정의할 수 없는 조사 항목

테스트를 별도 테스크로 만들었다면 제목을 `테스트 추가`처럼 쓰지 않는다. 예를 들어 `[FE][TASK] 결제 완료 흐름의 모바일 E2E·접근성 회귀 검증`처럼 독립 검증 대상, 환경, 완료 결과를 쓴다.

## 작성 기준

- 기능 부모는 프론트엔드 책임, 포함·제외 범위, 화면·상태·연동 영향, 완료 조건, 테스크 분리 판단을 기록한다.
- 하나의 테스크는 하나의 PR로 검토 가능한 변경 묶음이 원칙이다. 독립 배포·실험·롤백 단위가 다르면 분리한다.
- 테스크는 부모의 목적을 반복하지 않고, 자신이 제공하는 화면 또는 사용자 흐름의 결과와 경계를 명확히 한다.
- 디자인이 미확정이면 화면을 추정해 완결하지 말고, 필요한 상태와 `결정 필요` 항목을 기록한다.
- API가 필요하면 요청 시점, 로딩·성공·빈 결과·오류·권한 없음 상태, 계약 의존성을 작성한다.
- 개인정보, 토큰, 내부 URL, 운영 데이터가 들어간 캡처·로그를 이슈에 남기지 않는다.

## 분리 예시

`비로그인 찜 목록 유지` 기능의 프론트엔드 테스크는 `찜 버튼과 목록에서 비로그인 저장 상태를 표시·갱신`처럼 작성한다. 이 테스크에는 화면 상태, 실패 시 복구, 접근성·테스트를 둔다. 서버 저장 규칙과 API 구현은 백엔드 테스크로 둔다.
