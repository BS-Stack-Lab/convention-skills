다음 가이드는 결제·인증·권한 변경, DB 스키마 변경, 외부 시스템 연동, 대규모 리팩터링, 성능·보안 영향, 장애 가능성이 있는 변경에 적용합니다. 일반 PR보다 **변경의 의사결정 과정**, **장애 영향**, **배포와 복구 방법**을 구체적으로 남기는 것이 목적입니다.

## 작업 내용 / 이슈

### 작성 목적

해결하려는 문제뿐 아니라, 문제를 방치했을 때의 운영·사용자 영향을 명확히 합니다. 관련 이슈, 설계 문서, 장애 보고서도 함께 연결합니다.

### 예시

```markdown
- 관련 이슈: Closes #456
- 문제 상황: 결제사 일시 장애 시 결제 요청이 즉시 실패 처리되어 주문 이탈이 발생한다.
- 작업 목적: 일시적인 결제사 오류에 대해 안전한 재시도 정책을 적용한다.
- 변경이 필요한 이유: 결제 실패율을 낮추되 중복 결제를 방지해야 한다.
```

## 변경 요약

### 작성 목적

변경 전후의 동작과 핵심 설계 방식을 요약합니다. 구현 코드를 설명하는 대신, 주요 흐름과 안전장치를 작성합니다.

### 예시

```markdown
- 변경 전: 결제사 오류 발생 시 즉시 주문을 실패 처리한다.
- 변경 후: 재시도 가능한 오류에 한해 최대 3회 지수 백오프 재시도 후 실패 처리한다.
- 핵심 설계 또는 구현 방식: 결제 요청별 멱등 키를 사용해 재시도 중 중복 결제를 방지한다.
```

## 영향 범위

### 작성 목적

일반 PR보다 넓은 범위에서 영향을 검토합니다. 변경되는 영역뿐 아니라 장애가 발생했을 때 확산될 수 있는 영역과 변경하지 않은 안전 경계도 기록합니다.

### 작성 방법

- 사용자 기능 또는 화면: 고객이 경험하는 흐름과 오류 안내를 작성합니다.
- API / DB / 배치: 요청·응답 호환성, 스키마, 데이터 정합성, 배치 영향 여부를 작성합니다.
- 외부 시스템 또는 인프라: 결제사, 인증 제공자, 메시지 큐, 캐시, 모니터링 등 연동 대상을 작성합니다.
- 성능 / 보안 / 개인정보: 재시도 증가에 따른 부하, 권한·암호화·로그 노출 가능성을 작성합니다.
- 장애 발생 시 영향: 최악의 경우 어떤 기능과 사용자가 영향을 받는지 작성합니다.
- 변경 없음: 검토했으나 영향이 없었던 영역과 근거를 작성합니다.

### 예시

```markdown
- 사용자 기능 또는 화면: 결제 처리 중 로딩 시간이 최대 6초 증가할 수 있다.
- API / DB / 배치: 주문 상태 API의 응답 형식은 유지한다. 주문 이력에 재시도 횟수를 기록한다.
- 외부 시스템 또는 인프라: 결제사 API 호출 수가 일시적으로 증가할 수 있다.
- 성능 / 보안 / 개인정보: 결제 토큰은 로그에 기록하지 않는다. 재시도는 오류 코드별로 제한한다.
- 장애 발생 시 영향: 멱등 키 처리 오류 시 중복 결제 위험이 있으므로 결제 승인 상태를 우선 조회한다.
- 변경 없음: 회원가입 및 쿠폰 발급 흐름에는 영향이 없다.
```

## 리뷰어가 꼭 봐야 할 부분

### 작성 목적

리뷰어가 위험도가 높은 설계 판단에 시간을 집중할 수 있도록 안내합니다. 단순한 코드 위치보다 `무엇을 판단해야 하는지`와 `왜 해당 선택을 했는지`를 함께 작성합니다.

### 작성 방법

- `파일명:라인`에 핵심 코드 위치를 지정합니다.
- 고려한 대안과 채택하지 않은 이유를 기록합니다.
- 현재 방식을 선택한 근거를 수치, 정책, 호환성, 운영 제약과 함께 작성합니다.
- 알려진 제한 사항과 후속 작업을 숨기지 않고 기록합니다.

### 예시

```markdown
- `PaymentRetryHandler.java:45-72`: 재시도 대상 오류 코드와 최대 횟수 정의
  - 타임아웃과 5xx 응답만 재시도 대상으로 제한했는지 검토 부탁드립니다.
- 고려한 대안: 큐 기반 비동기 재처리
- 현재 방식을 선택한 이유: 기존 동기 결제 흐름과의 호환성을 유지하고, 결제 완료 응답을 즉시 제공해야 한다.
- 알려진 제한 사항 또는 후속 작업: 결제사 장애가 10분 이상 지속되는 경우를 위한 비동기 재처리 정책은 별도 이슈에서 다룬다.
```

## 테스트 방법

### 자동화 테스트 작성 방법

단위 테스트뿐 아니라 실패 경로, 경계 조건, 회귀 가능성이 큰 흐름을 함께 작성합니다. 실행 명령어와 결과, 새로 추가하거나 수정한 테스트 대상을 명시합니다.

### 자동화 테스트 예시

```markdown
- 실행 명령어: `./gradlew test integrationTest`
- 결과: unit test 128건, integration test 24건 전체 통과
- 추가·수정한 테스트:
  - 재시도 가능한 결제사 오류의 재호출 테스트
  - 최대 재시도 횟수 초과 시 주문 실패 처리 테스트
  - 동일 멱등 키 요청의 중복 결제 방지 테스트
```

### 수동 / 통합 테스트 작성 방법

테스트 환경, 사전 조건, 재현 단계, 기대 결과와 실제 결과를 분리해 작성합니다. 외부 시스템을 Mock 했는지, 개발·스테이징 환경에서 실제 연동했는지도 밝혀야 합니다.

### 수동 / 통합 테스트 예시

```markdown
- 테스트 환경: staging, 결제사 Sandbox
- 사전 조건: 테스트 카드와 재시도 대상 오류를 반환하는 Mock 응답 설정

1. 결제 요청 중 첫 번째 호출에서 503 응답을 반환한다.
2. 동일 주문으로 결제를 계속 진행한다.
3. 두 번째 호출에서 승인 응답을 반환한다.

- 기대 결과:
  - 최대 3회 내에서만 재시도한다.
  - 주문은 한 번만 결제 완료 상태로 변경된다.
  - 결제 토큰과 카드 정보가 로그에 남지 않는다.
- 실제 결과: 기대 결과와 동일하게 동작함
```

## 배포 및 롤백 계획

### 작성 목적

코드가 병합된 뒤 안전하게 배포하고, 문제가 발생했을 때 복구할 방법을 사전에 합의합니다. DB나 외부 시스템 변경이 있으면 특히 필수입니다.

### 작성 방법

- 배포 전 확인 사항: 모니터링 대시보드, 알림, 권한, 설정값, 백업 여부를 작성합니다.
- 배포 순서: 마이그레이션, 애플리케이션, 설정 변경의 선후 관계를 작성합니다.
- Feature Flag 사용 여부: 플래그 이름, 기본값, 활성화 범위와 해제 조건을 작성합니다.
- 마이그레이션 여부: 정방향·역방향 호환성, 데이터 백필, 잠금 가능성을 작성합니다.
- 롤백 방법: 코드 롤백만으로 되는지, 데이터 복구가 필요한지, 어떤 지표를 기준으로 판단하는지 작성합니다.

### 예시

```markdown
- 배포 전 확인 사항: 결제 실패율·중복 승인 건수·결제사 API 지연 시간 대시보드와 알림을 확인한다.
- 배포 순서: DB에 재시도 이력 컬럼을 먼저 추가한 뒤 애플리케이션을 배포한다.
- Feature Flag 사용 여부: `payment-retry-enabled`, 기본값 `false`, 내부 테스트 계정부터 활성화한다.
- 마이그레이션 여부: 있음. 컬럼 추가만 수행하므로 이전 버전 애플리케이션과 호환된다.
- 롤백 방법: 플래그를 즉시 비활성화하고, 필요 시 애플리케이션 이전 버전으로 롤백한다. 이미 기록된 재시도 이력 데이터는 유지한다.
```

## 스크린샷 또는 데모

### 작성 목적

사용자 화면, 운영 도구, CLI 출력처럼 눈으로 검증 가능한 변경을 보여줍니다. UI 변경이 없더라도 운영 대시보드나 API 응답 변화가 핵심이라면 마스킹한 캡처나 요청·응답 예시를 첨부할 수 있습니다.

### 작성 방법

- UI·사용자 흐름·CLI 출력 변경 시 변경 전후를 첨부합니다.
- 운영 화면이라면 고객 정보·토큰·내부 URL을 마스킹합니다.
- 화면 변경이 없으면 `해당 없음`으로 작성합니다.

### 작성 목적
