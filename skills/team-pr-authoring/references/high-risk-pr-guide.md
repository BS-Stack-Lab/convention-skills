# 복잡하거나 위험한 PR 작성 가이드

결제·인증·권한 변경, DB 스키마 변경, 외부 시스템 연동, 대규모 리팩터링, 성능·보안·개인정보 영향, 장애 가능성이 있는 변경에 적용한다. 일반 PR보다 의사결정 과정, 장애 영향, 배포와 복구 방법을 구체적으로 남긴다.

## 작업 내용 / 이슈

문제와 함께 방치했을 때의 사용자·운영 영향을 적고, 관련 이슈·설계 문서·장애 보고서를 연결한다.

```markdown
- 관련 이슈: Closes #456
- 문제 상황: 결제사 일시 장애 시 결제 요청이 즉시 실패 처리되어 주문 이탈이 발생한다.
- 작업 목적: 일시적인 결제사 오류에 안전한 재시도 정책을 적용한다.
- 변경이 필요한 이유: 결제 실패율을 낮추되 중복 결제를 방지해야 한다.
```

## 변경 요약

변경 전후와 핵심 안전장치를 설명한다. 구현 코드의 순서가 아니라 주요 흐름과 설계 결정을 요약한다.

```markdown
- 변경 전: 결제사 오류 발생 시 즉시 주문을 실패 처리한다.
- 변경 후: 재시도 가능한 오류에 한해 최대 3회 지수 백오프 재시도 후 실패 처리한다.
- 핵심 설계 또는 구현 방식: 결제 요청별 멱등 키로 재시도 중 중복 결제를 방지한다.
```

## 영향 범위

변경 영역, 장애 확산 영역, 검토했지만 변경하지 않은 안전 경계를 작성한다.

- 사용자 기능 또는 화면: 고객이 겪는 흐름, 대기 시간, 오류 안내
- API / DB / 배치: 요청·응답 호환성, 스키마, 정합성, 배치 영향
- 외부 시스템 또는 인프라: 결제사, 인증 제공자, 메시지 큐, 캐시, 모니터링
- 성능 / 보안 / 개인정보: 부하, 권한, 암호화, 로그 노출
- 장애 발생 시 영향: 최악의 영향과 완화 수단
- 변경 없음: 검토 근거가 있는 안전 경계

```markdown
- 사용자 기능 또는 화면: 결제 처리 중 로딩 시간이 최대 6초 증가할 수 있다.
- API / DB / 배치: 주문 상태 API 응답은 유지하고, 주문 이력에 재시도 횟수를 기록한다.
- 외부 시스템 또는 인프라: 결제사 API 호출 수가 일시적으로 증가할 수 있다.
- 성능 / 보안 / 개인정보: 결제 토큰은 로그에 기록하지 않고, 오류 코드별로 재시도를 제한한다.
- 장애 발생 시 영향: 멱등 키 처리 오류의 중복 결제 위험은 결제 승인 상태를 우선 조회해 완화한다.
- 변경 없음: 회원가입 및 쿠폰 발급 흐름은 변경하지 않는다.
```

## 리뷰어가 꼭 봐야 할 부분

고위험 설계 판단에 리뷰 시간을 집중할 수 있도록 파일 위치, 판단 대상, 트레이드오프, 알려진 제한 사항을 쓴다.

```markdown
- `PaymentRetryHandler.java:45-72`: 재시도 대상 오류 코드와 최대 횟수 정의
  - 타임아웃과 5xx 응답만 재시도 대상으로 제한했는지 검토 부탁드립니다.
- 고려한 대안: 큐 기반 비동기 재처리
- 현재 방식을 선택한 이유: 기존 동기 결제 흐름 호환성과 즉시 완료 응답을 유지해야 한다.
- 알려진 제한 사항 또는 후속 작업: 10분 이상 지속되는 결제사 장애의 비동기 재처리는 별도 이슈에서 다룬다.
```

## 테스트 방법

단위 테스트뿐 아니라 실패 경로, 경계 조건, 회귀 위험이 큰 흐름을 기록한다. 실행 명령어·결과·변경한 테스트 대상을 명시한다.

```markdown
- 실행 명령어: `./gradlew test integrationTest`
- 결과: unit test 128건, integration test 24건 전체 통과
- 추가·수정한 테스트:
  - 재시도 가능한 결제사 오류 재호출 테스트
  - 최대 재시도 횟수 초과 시 주문 실패 처리 테스트
  - 동일 멱등 키 요청의 중복 결제 방지 테스트
```

수동·통합 테스트에는 환경, 사전 조건, Mock 여부, 실제 연동 여부를 밝히고 절차와 결과를 구분한다.

```markdown
- 테스트 환경: staging, 결제사 Sandbox
- 사전 조건: 테스트 카드와 재시도 대상 오류를 반환하는 Mock 응답 설정

1. 첫 결제 호출에서 503 응답을 반환한다.
2. 동일 주문 결제를 계속 진행한다.
3. 두 번째 호출에서 승인 응답을 반환한다.

- 기대 결과:
  - 최대 3회 내에서만 재시도한다.
  - 주문은 한 번만 결제 완료 상태로 변경된다.
  - 결제 토큰과 카드 정보가 로그에 남지 않는다.
- 실제 결과: 기대 결과와 동일하게 동작함
```

## 배포 및 롤백 계획

병합 뒤 안전하게 배포하고 문제가 생기면 복구할 방법을 사전에 합의한다. DB·외부 시스템 변경에는 필수다.

- 배포 전 확인 사항: 대시보드·알림·권한·설정값·백업
- 배포 순서: 마이그레이션, 애플리케이션, 설정의 선후 관계
- Feature Flag: 이름, 기본값, 활성화 범위, 해제 조건
- 마이그레이션: 정·역방향 호환성, 백필, 잠금 가능성
- 롤백 방법: 코드 롤백·데이터 복구 필요 여부·판단 지표

```markdown
- 배포 전 확인 사항: 결제 실패율·중복 승인 건수·결제사 API 지연 시간 대시보드와 알림을 확인한다.
- 배포 순서: 재시도 이력 컬럼을 먼저 추가한 뒤 애플리케이션을 배포한다.
- Feature Flag 사용 여부: `payment-retry-enabled`, 기본값 `false`, 내부 테스트 계정부터 활성화한다.
- 마이그레이션 여부: 있음. 컬럼 추가만 수행하므로 이전 애플리케이션과 호환된다.
- 롤백 방법: 플래그를 즉시 비활성화하고, 필요 시 이전 버전으로 롤백한다. 재시도 이력은 유지한다.
```

## 스크린샷·체크리스트

UI, 운영 도구, CLI 출력, API 응답처럼 눈으로 검증할 변화가 있으면 민감 정보를 마스킹해 첨부한다. 체크리스트는 근거를 대체하지 않으며, 미수행 항목에는 이유와 후속 계획을 남긴다.
