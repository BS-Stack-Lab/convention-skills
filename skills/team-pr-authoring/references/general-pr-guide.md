이 문서는 일반 PR의 각 항목을 일관되고 재현 가능하게 작성하기 위한 가이드입니다. 코드의 세부 구현을 나열하기보다 변경의 목적, 영향, 검증 방법을 중심으로 작성합니다.

---

## 작업 내용 / 이슈

### 작성 목적

작업의 배경과 목적을 작성합니다. 코드가 무엇을 바꿨는지보다 왜 이 작업이 필요한지를 먼저 설명합니다.

### 작성 방법

- 관련 이슈가 있으면 `Closes #번호` 형식으로 연결합니다.
- 이슈가 없다면 해결하려는 문제를 한두 문장으로 작성합니다.
- 구현 내용만 나열하지 말고 사용자 또는 운영상 문제를 함께 작성합니다.

### 예시

```markdown
- 관련 이슈: Closes #123
- 작업 목적: 로그인 실패 원인을 사용자가 알 수 있도록 오류 안내를 개선한다.
```

### 피해야 할 표현

```markdown
- 로그인 기능 수정
```

## 변경 요약

### 작성 목적

변경 전과 후를 비교할 수 있게 작성합니다. 파일명이나 함수명 나열보다 기능 변화가 핵심입니다.

### 작성 방법

- 1\~3개의 핵심 항목으로 짧게 작성합니다.
- 리뷰어가 코드를 열기 전 변경 결과를 이해할 수 있어야 합니다.
- 리팩터링이라면 외부 동작 변화가 없음을 분명히 적습니다.

### 예시

```markdown
- 변경 전: 로그인 실패 시 모든 오류에 동일한 안내 문구를 표시했다.
- 변경 후: 비밀번호 오류, 계정 잠금, 네트워크 오류에 따라 서로 다른 안내 문구를 표시한다.
```

```markdown
- 변경 전: 주문 상태 변경 로직이 여러 서비스에 중복되어 있었다.
- 변경 후: 공통 서비스로 통합했다. 외부 API와 사용자 동작에는 변화가 없다.
```

### 피해야 할 표현

```markdown
- PaymentService 수정
```

## 영향 범위

### 작성 목적

이번 변경으로 영향을 받는 영역과 영향을 받지 않는 영역을 작성합니다. 회귀 테스트 범위를 정하고, 리뷰어가 위험 지점을 빠르게 파악하는 데 도움이 됩니다.

### 작성 방법

필요한 경우 다음을 확인합니다.

- 사용자 화면 및 사용자 흐름
- API 요청·응답
- DB 스키마와 데이터 마이그레이션
- 배치 작업, 캐시, 메시지 큐
- 결제, 인증, 권한
- 외부 API 또는 인프라
- 성능, 보안, 개인정보

영향이 없다면 단순히 `없음`만 쓰기보다 그 이유를 작성합니다.

### 예시

```markdown
- 영향받는 기능 또는 화면: 로그인 화면, 계정 잠금 안내 화면
- API / DB / 외부 연동: 로그인 API 오류 코드 처리 방식 변경
- 영향 없음: 회원가입, 자동 로그인, 소셜 로그인
```

```markdown
- 영향 없음: 내부 코드 정리만 수행했으며 API 요청·응답과 화면 동작은 변경하지 않았다.
```

## 리뷰어가 꼭 봐야 할 부분 (선택)

### 작성 목적

작성자가 특히 검토받고 싶은 설계 판단, 예외 처리, 호환성 문제를 안내합니다. 이 항목이 없으면 `해당 없음`으로 작성합니다.

### 작성 방법

- 코드 위치와 검토가 필요한 이유를 함께 작성합니다.
- 선택한 방식과 고려했던 대안을 밝힙니다.
- 리뷰어에게 답을 원하는 질문을 구체적으로 적습니다.

다음 상황에 작성하면 좋습니다.

- 여러 구현 방식 중 하나를 선택한 경우
- 레거시 코드와 호환성을 유지해야 하는 경우
- 예외 처리, 동시성, 성능, 보안이 중요한 경우
- 테스트하기 어렵거나 재현 조건이 복잡한 경우
- 리뷰어의 설계 의견이 필요한 경우

### 예시

```markdown
- `LoginErrorMapper.ts:42`
  - 서버 오류 코드를 화면용 메시지로 변환하는 분기입니다.
  - 기존 클라이언트와의 호환성을 위해 기본 오류 메시지를 유지했습니다.
  - 알 수 없는 오류 코드도 기본 메시지로 처리하는 방식이 적절한지 검토 부탁드립니다.
```

### 피해야 할 표현

```markdown
- 전체 확인 부탁드립니다.
```

## 테스트 방법

### 작성 목적

리뷰어가 같은 환경에서 변경 사항을 재현하고 검증할 수 있도록 작성합니다. 단순히 "테스트 완료"라고 적지 않고 실행 방법과 결과를 함께 남깁니다.

### 자동화 테스트 작성 방법

- 실행한 테스트 명령어와 결과를 작성합니다.
- 추가하거나 수정한 테스트가 있다면 대상을 함께 작성합니다.
- 실행하지 못했다면 이유와 대체 검증 방법을 명시합니다.

### 자동화 테스트 예시

```markdown
- 실행 명령어: `npm run test:unit`
- 결과: 42개 테스트 전체 통과
- 추가·수정한 테스트:
  - 로그인 오류 코드별 안내 문구 노출 테스트 추가
  - 네트워크 오류 발생 시 재시도 버튼 노출 테스트 추가
```

### 테스트 미실행 예시

```markdown
- 미실행 사유: 테스트 환경에서 외부 인증 서버 연결이 불가능했다.
- 대체 검증: 개발 환경에서 오류 응답을 Mock 처리하여 수동 검증했다.
```

### 수동 테스트 작성 방법

- 사전 조건을 먼저 작성합니다.
- 테스트 단계를 번호로 나눕니다.
- 기대 결과와 실제 결과를 구분합니다.

### 수동 테스트 예시

```markdown
- 사전 조건: 테스트 계정이 존재하고 로그인 화면에 접근 가능한 상태

1. 잘못된 비밀번호를 입력한다.
2. 로그인 버튼을 클릭한다.
3. 네트워크 연결을 해제한 후 다시 로그인한다.

- 기대 결과:
  - 잘못된 비밀번호 입력 시 비밀번호 오류 문구가 표시된다.
  - 네트워크 연결 해제 시 네트워크 오류 문구가 표시된다.

- 실제 결과: 기대 결과와 동일하게 동작함
```

## 스크린샷 또는 데모

### 작성 목적

UI, 사용자 흐름, CLI 출력처럼 사용자가 보게 되는 결과가 바뀌었을 때 첨부합니다. 가능하면 변경 전후를 나란히 보여줍니다.

### 작성 방법

- 화면 변경: 변경 전후 화면을 첨부합니다.
- 동작 흐름 변경: GIF, 영상 또는 단계별 이미지를 첨부합니다.
- CLI 변경: 변경 전후 터미널 출력을 첨부합니다.
- UI 변경이 없으면 `해당 없음`으로 작성합니다.
- 실제 고객 정보, 토큰, 전화번호, 주문번호 등 민감 정보는 반드시 마스킹합니다.

### 예시

```markdown
| 변경 전 | 변경 후 |
| --- | --- |
| 모든 로그인 오류에 동일한 문구 표시 | 오류 유형별 안내 문구 표시 |
| 이미지 첨부 | 이미지 첨부 |
```

## 체크리스트

### 작성 목적

PR 작성자가 병합 전 기본 요건을 직접 점검하는 항목입니다. 코드 품질을 보장하는 장치라기보다 리뷰 전에 놓치기 쉬운 사항을 확인하는 마지막 안전망으로 사용합니다.

### 작성 방법

- 수행한 항목만 체크합니다.
- 해당하지 않는 항목은 팀 규칙에 따라 `해당 없음` 사유를 남깁니다.
- 체크리스트만 채우고 본문의 설명을 생략하지 않습니다.

### 예시

```markdown
- [x] 하나의 목적에 집중된 PR입니다.
- [x] 필요한 테스트를 추가·수정하고 실행했습니다.
- [x] UI 변경 시 스크린샷 또는 데모를 첨부했습니다.
- [x] 민감 정보, 디버그 코드, 불필요한 파일이 포함되지 않았습니다.
```
