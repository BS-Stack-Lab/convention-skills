이 문서는 일반 PR의 각 항목을 일관되고 재현 가능하게 작성하기 위한 가이드입니다. 코드의 세부 구현을 나열하기보다 변경의 목적, 영향, 검증 방법을 중심으로 작성합니다.

---

## 작업 내용 / 이슈

### 작성 목적

작업의 배경과 목적을 작성합니다. 코드가 무엇을 바꿨는지보다 왜 이 작업이 필요한지를 먼저 설명합니다.

### 작성 방법

- 관련 이슈가 있으면 `Closes #번호` 형식으로 연결합니다.
- 이슈가 없다면 해결하려는 문제를 한두 문장으로 작성합니다.
- 구현 내용만 나열하지 말고 사용자 또는 운영상 문제를 함께 작성합니다.

### 예시

```markdown
- 관련 이슈: Closes #123
- 작업 목적: 로그인 실패 원인을 사용자가 알 수 있도록 오류 안내를 개선한다.
```

### 피해야 할 표현

```markdown
- 로그인 기능 수정
```

---

## 변경 요약

### 작성 목적

변경 전과 후를 비교할 수 있게 작성합니다. 파일명이나 함수명 나열보다 기능 변화가 핵심입니다.

### 작성 방법

- 1\~3개의 핵심 항목으로 짧게 작성합니다.
- 리뷰어가 코드를 열기 전 변경 결과를 이해할 수 있어야 합니다.
- 리팩터링이라면 외부 동작 변화가 없음을 분명히 적습니다.

### 예시

```markdown
- 변경 전: 로그인 실패 시 모든 오류에 동일한 안내 문구를 표시했다.
- 변경 후: 비밀번호 오류, 계정 잠금, 네트워크 오류에 따라 서로 다른 안내 문구를 표시한다.
```

```markdown
- 변경 전: 주문 상태 변경 로직이 여러 서비스에 중복되어 있었다.
- 변경 후: 공통 서비스로 통합했다. 외부 API와 사용자 동작에는 변화가 없다.
```

### 피해야 할 표현

```markdown
- PaymentService 수정
```

## 영향 범위

### 작성 목적

이번 변경으로 영향을 받는 영역과 영향을 받지 않는 영역을 작성합니다. 회귀 테스트 범위를 정하고, 리뷰어가 위험 지점을 빠르게 파악하는 데 도움이 됩니다.

### 작성 방법

필요한 경우 다음을 확인합니다.

- 사용자 화면 및 사용자 흐름
- API 요청·응답
- DB 스키마와 데이터 마이그레이션
- 배치 작업, 캐시, 메시지 큐
- 결제, 인증, 권한
- 외부 API 또는 인프라
- 성능, 보안, 개인정보

영향이 없다면 단순히 `없음`만 쓰기보다 그 이유를 작성합니다.

### 예시

```markdown
- 영향받는 기능 또는 화면: 로그인 화면, 계정 잠금 안내 화면
- API / DB / 외부 연동: 로그인 API 오류 코드 처리 방식 변경
- 영향 없음: 회원가입, 자동 로그인, 소셜 로그인
```

```markdown
- 영향 없음: 내부 코드 정리만 수행했으며 API 요청·응답과 화면 동작은 변경하지 않았다.
```

## 체크리스트

### 작성 목적

PR 작성자가 병합 전 기본 요건을 직접 점검하는 항목입니다. 코드 품질을 보장하는 장치라기보다 리뷰 전에 놓치기 쉬운 사항을 확인하는 마지막 안전망으로 사용합니다.

### 작성 방법

- 수행한 항목만 체크합니다.
- 해당하지 않는 항목은 팀 규칙에 따라 `해당 없음` 사유를 남깁니다.
- 체크리스트만 채우고 본문의 설명을 생략하지 않습니다.

### 예시

```markdown
- [x] 하나의 목적에 집중된 PR입니다.
- [x] 필요한 테스트를 추가·수정하고 실행했습니다.
- [x] UI 변경 시 스크린샷 또는 데모를 첨부했습니다.
- [x] 민감 정보, 디버그 코드, 불필요한 파일이 포함되지 않았습니다.
```
