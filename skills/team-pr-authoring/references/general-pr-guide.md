# 일반 PR 작성 가이드

일반 PR은 코드의 세부 구현을 나열하지 않는다. 변경 목적, 기능 변화, 영향 범위, 검증 방법을 리뷰어가 재현할 수 있게 남긴다.

## 작업 내용 / 이슈

변경한 코드가 아니라 작업의 배경과 목적을 먼저 작성한다.

- 관련 이슈가 있으면 `Closes #번호`로 연결한다.
- 이슈가 없으면 해결하려는 사용자 또는 운영상 문제를 한두 문장으로 쓴다.
- `로그인 기능 수정`처럼 구현만 나열하지 않는다.

좋은 예시:

```markdown
- 관련 이슈: Closes #123
- 작업 목적: 로그인 실패 원인을 사용자가 알 수 있도록 오류 안내를 개선한다.
```

## 변경 요약

리뷰어가 파일을 열기 전에 결과를 이해할 수 있도록 변경 전후를 1~3개 항목으로 비교한다.

- 파일명, 클래스명, 함수명만 나열하지 않는다.
- 리팩터링은 외부 API·화면·사용자 동작 변화가 없음을 명시한다.

좋은 예시:

```markdown
- 변경 전: 로그인 실패 시 모든 오류에 동일한 안내 문구를 표시했다.
- 변경 후: 비밀번호 오류, 계정 잠금, 네트워크 오류에 따라 서로 다른 안내 문구를 표시한다.
```

## 영향 범위

변경되는 영역과 변경하지 않은 안전 경계를 모두 적는다. 필요하면 다음을 검토한다.

- 사용자 화면과 사용자 흐름
- API 요청·응답
- DB 스키마·데이터 마이그레이션
- 배치, 캐시, 메시지 큐
- 결제, 인증, 권한
- 외부 API·인프라
- 성능, 보안, 개인정보

영향이 없으면 `없음`만 쓰지 말고 근거를 쓴다.

좋은 예시:

```markdown
- 영향받는 기능 또는 화면: 로그인 화면, 계정 잠금 안내 화면
- API / DB / 외부 연동: 로그인 API 오류 코드 처리 방식 변경
- 영향 없음: 회원가입, 자동 로그인, 소셜 로그인은 요청·응답과 화면 흐름을 변경하지 않았다.
```

## 리뷰어가 꼭 봐야 할 부분

설계 판단, 예외 처리, 호환성, 동시성, 성능, 보안, 재현이 어려운 조건처럼 집중 검토가 필요한 경우에만 작성한다. 없으면 `해당 없음`으로 쓴다.

- 코드 위치, 검토할 판단, 선택 이유를 함께 쓴다.
- 고려한 대안과 리뷰어에게 원하는 질문을 구체화한다.
- `전체 확인 부탁드립니다`는 사용하지 않는다.

좋은 예시:

```markdown
- `LoginErrorMapper.ts:42`
  - 서버 오류 코드를 화면 메시지로 변환하는 분기다.
  - 기존 클라이언트 호환성을 위해 기본 오류 메시지를 유지했다.
  - 알 수 없는 오류 코드도 기본 메시지로 처리하는 방식이 적절한지 검토 부탁드립니다.
```

## 테스트 방법

리뷰어가 같은 환경에서 검증할 수 있도록 명령어·조건·절차·결과를 남긴다.

자동화 테스트에는 실행 명령어, 결과, 추가·수정한 테스트 대상을 쓴다.

```markdown
- 실행 명령어: `npm run test:unit`
- 결과: 42개 테스트 전체 통과
- 추가·수정한 테스트:
  - 로그인 오류 코드별 안내 문구 노출 테스트 추가
  - 네트워크 오류 시 재시도 버튼 노출 테스트 추가
```

실행하지 못했으면 사유와 대체 검증을 사실대로 쓴다.

```markdown
- 미실행 사유: 테스트 환경에서 외부 인증 서버 연결이 불가능했다.
- 대체 검증: 개발 환경에서 오류 응답을 Mock 처리하여 수동 검증했다.
```

수동 테스트에는 사전 조건, 번호가 있는 절차, 기대 결과, 실제 결과를 분리한다.

```markdown
- 사전 조건: 테스트 계정이 존재하고 로그인 화면에 접근 가능한 상태

1. 잘못된 비밀번호를 입력한다.
2. 로그인 버튼을 클릭한다.
3. 네트워크 연결을 해제한 후 다시 로그인한다.

- 기대 결과:
  - 비밀번호 오류와 네트워크 오류에 맞는 문구가 표시된다.
- 실제 결과: 기대 결과와 동일하게 동작함
```

## 스크린샷 또는 데모

UI, 사용자 흐름, CLI 출력처럼 사용자가 보는 결과가 변하면 변경 전후를 첨부한다. 흐름 변화는 GIF·영상·단계별 이미지도 가능하다. UI 변화가 없으면 `해당 없음`으로 쓴다. 고객 정보, 토큰, 전화번호, 주문번호는 반드시 마스킹한다.

## 체크리스트

체크리스트는 본문을 대체하지 않는 마지막 확인이다. 수행한 항목만 체크하고, 해당하지 않는 항목은 팀 규칙에 따라 사유를 남긴다.
