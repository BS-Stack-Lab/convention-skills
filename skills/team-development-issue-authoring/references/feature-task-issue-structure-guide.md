# 영역별 기능 이슈와 하위 테스크 이슈 구조 가이드

## 목적과 관계

백엔드 기능 이슈와 프론트엔드 기능 이슈는 각각 `해당 영역에서 무엇을 왜 제공하는가`를 합의하는 부모 이슈다. 하위 테스크 이슈는 그 부모 기능 이슈의 범위가 독립 작업으로 나뉠 때만 만드는 자식 이슈다.

```text
[BE][FEATURE] 백엔드가 제공할 사용자·시스템 결과
├── [BE][TASK] API·도메인·데이터 변경
└── [BE][TASK] 독립 검증·외부 연동·마이그레이션

[FE][FEATURE] 프론트엔드가 제공할 사용자 결과
├── [FE][TASK] 화면·상태·사용자 흐름 변경
└── [FE][TASK] 독립 E2E·접근성·디자인 검증
```

공통 기능 요구가 백엔드와 프론트엔드 모두에 영향을 주면 `[BE][FEATURE]`와 `[FE][FEATURE]`를 각각 만들고 서로 관련 이슈로 연결한다. 공통 `[FEATURE]` 하나 아래에 BE·FE 테스크를 섞지 않는다. 각 기능 부모와 테스크는 같은 영역 접두사를 사용한다.

## 자동 분리 규칙

기능·개선·리팩터링 이슈를 작성하거나 수정할 때 다음을 적용한다.

- 사용자가 `백엔드`를 지정하면 `[BE][FEATURE]` 초안을 작성하고, 테스크 분리 기준을 충족하는 경우에만 `[BE][TASK]` 초안을 추가한다.
- 사용자가 `프론트엔드`를 지정하면 `[FE][FEATURE]` 초안을 작성하고, 테스크 분리 기준을 충족하는 경우에만 `[FE][TASK]` 초안을 추가한다.
- 사용자가 영역을 지정하지 않으면 `[BE][FEATURE]`와 `[FE][FEATURE]` 초안을 모두 작성한다. 각 부모에서 실제로 분리해야 하는 작업만 해당 영역의 테스크로 작성한다.
- 요청, 설계 문서, 저장소 구조 또는 변경 대상에서 백엔드와 프론트엔드 모두에 영향이 확인되면 두 기능 부모를 모두 작성한다. 한쪽의 작업이 실제로 필요 없다는 근거가 확인되면 해당 기능 부모를 만들지 않고 관련 이슈에 이유를 남긴다.
- DB, 인프라, QA, 문서가 독립적인 완료·검토 단위라면 해당 영역의 부모 아래에 별도 테스크 이슈로 제안한다. 사용자가 요청하지 않은 이슈를 GitHub에 실제 생성하지는 않는다.

`자동 작성`은 이슈 초안과 관계 계획을 만드는 것을 뜻한다. GitHub 이슈 생성, 하위 이슈 연결, 담당자·라벨·프로젝트 변경은 외부 상태 변경이므로 사용자의 명시적 요청 후에만 실행한다.

## 기능 부모 이슈 작성 기준

기능 부모 이슈에는 문제, 해당 영역의 사용자·시스템 결과, 포함·제외 범위, 테스트 가능한 완료 조건, 의존성, 테스크 분리 판단만 기록한다. 클래스·컴포넌트·SQL 파일 목록은 실제로 분리한 각 테스크 이슈에 둔다.

GitHub 이슈 관계 기능을 사용할 수 있으면 부모와 하위 이슈 관계를 연결한다. 단순 체크리스트는 진행 현황 표시로 쓸 수 있지만, 독립적인 담당·논의·PR·상태 추적이 필요한 작업은 별도 이슈로 만든다. GitHub는 작업 목록 항목을 이슈로 전환할 수 있고, 부모-하위 이슈 트리를 생성하는 기능도 제공한다.

## 테스크 이슈를 만들기 전 판정

테스크 이슈는 기능 부모의 본문 섹션을 그대로 옮기는 용도가 아니다. 아래 중 하나 이상이 성립할 때만 분리한다.

- 기능 부모의 범위가 하나의 PR·한 명의 담당자·하나의 리뷰 흐름으로 완료하기에 크다.
- 독립적인 담당자, 선행·후행 관계, 배포 순서 또는 외부 의존성이 있어 별도 상태 추적이 필요하다.
- DB Migration, 외부 연동, 권한·보안, 성능 검증처럼 위험·검토·롤백 기준이 독립적이다.
- 통합·E2E·접근성·계약·운영 검증이 구현 작업과 다른 환경·담당자·일정으로 운영되어 별도 완료 조건과 증빙이 필요하다.
- 문서·디자인·QA 작업이 독립 배정되어야 하며, 완료하지 않으면 기능 부모를 닫을 수 없다.

다음은 테스크로 분리하지 않는다.

- 같은 담당자가 같은 PR에서 구현과 함께 수행하는 단위 테스트·린트·간단한 문서 갱신
- 단지 본문에 API, 화면, 테스트라는 항목이 있다는 이유만으로 나눈 작업
- 부모의 요구와 완료 조건이 아직 확정되지 않아 독립 결과를 정의할 수 없는 작업

백엔드·프론트엔드별 판단 기준과 부모·테스크 템플릿은 각 영역 스킬의 가이드를 따른다.

## 테스크 이슈의 공통 기준

- 같은 영역의 상위 기능 이슈 링크와 이 테스크의 책임 경계를 첫 부분에 쓴다.
- 제목은 `[BE][TASK]` 또는 `[FE][TASK]`와 결과 중심 문장을 사용한다.
- 포함·제외 범위, 완료 조건, 의존성, 검증 계획을 독립적으로 작성한다.
- 서로 다른 배포·검토 단위를 하나의 테스크에 섞지 않는다.
- 완료 조건이 상위 기능 이슈의 완료 조건과 모순되면 상위 이슈를 먼저 갱신하거나 `결정 필요`로 남긴다.

## 공개 사례 조사 메모

기업별 세부 이슈 템플릿·명칭은 대개 비공개다. 확인 가능한 공개 자료와 이 가이드에서 채택한 원칙은 [국내외 공개 사례 조사](company-issue-practices.md)에 분리해 기록한다. 해당 자료는 특정 회사의 내부 규칙을 추정하는 근거로 사용하지 않는다.
