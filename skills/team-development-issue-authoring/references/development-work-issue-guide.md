# 개발 전 작업 이슈 작성 가이드

개발 전에 기능의 목적, 범위, 완료 기준, 세부 작업을 합의하기 위한 부모 이슈 양식입니다. 이 이슈는 "무엇을 왜 만드는가"를 설명하고, 실제 구현은 하위 이슈로 나눠 진행합니다.

## 작성 전에 결정할 것

이슈를 열기 전에 아래 질문에 답할 수 있어야 합니다.

1. 누가 어떤 상황에서 겪는 문제인가?
2. 이번 작업이 끝나면 사용자가 무엇을 할 수 있는가?
3. 이번 배포에 포함하지 않을 것은 무엇인가?
4. 어느 조건을 만족해야 완료로 볼 수 있는가?
5. API, 화면, 테스트, 문서 중 어떤 독립 작업이 필요한가?

답하기 어려운 항목은 빈칸으로 두기보다 `결정 필요`라고 쓰고 담당자 또는 논의 채널을 남깁니다.

## 항목별 작성 방법

### 1. 제목

형식은 `[유형] 기능 또는 결과`를 권장합니다. 제목만 읽어도 목적을 이해할 수 있어야 합니다.

- 좋은 예: `[FEATURE] 비로그인 사용자의 찜 목록 저장`
- 좋은 예: `[FEATURE] 검색 결과를 가격순으로 정렬`
- 피해야 할 예: `[FEATURE] 찜 기능 작업`
- 피해야 할 예: `검색 관련 수정`

`FEATURE`, `IMPROVEMENT`, `REFACTOR`처럼 팀에서 합의한 유형을 사용합니다. 구현 방식이나 담당자 이름은 제목보다 본문에 적습니다.

### 2. 목적

문제와 기대 결과를 각각 한두 문장으로 적습니다. 구현 방법 대신 사용자 또는 비즈니스 결과를 씁니다.

- 좋은 예: `비로그인 사용자는 페이지를 벗어나면 찜한 상품을 잃는다. 브라우저에 임시 저장해 다음 방문에서도 목록을 유지한다.`
- 피해야 할 예: `localStorage를 추가한다.`

### 3. 사용자 시나리오

한 명의 사용자가 기능을 사용하는 흐름을 "언제 - 무엇을 - 어떤 결과" 순서로 작성합니다.

- 좋은 예: `비로그인 사용자가 상품 A를 찜한 뒤 새로고침하면, 상품 A가 찜 목록에 남아 있다.`
- 좋은 예: `로그인한 사용자가 찜을 취소하면, 화면과 서버의 찜 목록에서 모두 제거된다.`
- 피해야 할 예: `찜 기능이 정상 동작한다.`

### 4. 범위

`포함`에는 이번 이슈에서 반드시 구현할 행동과 화면을, `제외`에는 나중에 할 요구를 적습니다. 범위가 길어지면 불필요한 논쟁과 재작업을 줄일 수 있습니다.

- 포함 예: `상품 상세와 검색 결과 카드에서 찜 추가와 취소`
- 제외 예: `찜 목록 폴더 분류`, `푸시 알림`, `다른 기기 간 비로그인 찜 동기화`

### 5. 완료 조건

완료 조건은 테스트 가능한 문장으로 씁니다. "구현 완료"처럼 판단 기준이 없는 표현은 사용하지 않습니다.

- 좋은 예: `사용자가 찜 버튼을 누르면 목록 수와 버튼 상태가 즉시 변경된다.`
- 좋은 예: `네트워크 요청 실패 시 기존 상태를 복구하고 오류 메시지를 표시한다.`
- 좋은 예: `로그인과 비로그인 상태의 동작을 각각 테스트한다.`
- 피해야 할 예: `예외 처리한다.`

완료 조건에는 기능 정상 흐름, 예외 흐름, 테스트 또는 리뷰 기준을 최소 하나씩 넣습니다.

### 6. 작업 현황과 하위 이슈

한 사람, 한 PR, 한 테스트 단위로 독립 완료할 수 있으면 하위 이슈로 만듭니다. 부모 이슈의 체크박스에는 하위 이슈 링크를 넣습니다.

- 하위 이슈로 분리: API 구현, 화면 구현, 데이터 마이그레이션, E2E 테스트, 운영 문서 변경
- 체크박스로 유지: API 응답 필드 확인, 디자인 링크 확인처럼 짧고 독립 배정이 필요 없는 일

각 하위 이슈에는 담당자, 예상 소요 시간, 관련 PR을 남깁니다. GitHub에서는 `- [ ] #123` 형태로 연결하면 하위 이슈 종료 시 체크박스를 자동 완료할 수 있습니다.

### 7. 의존성 및 블로커

선행 이슈, 디자인 확정, 외부 API 계약, 권한 요청처럼 시작 또는 완료를 막는 요소를 적습니다.

- 좋은 예: `선행 이슈: #41 로그인 상태 조회 API 완료 후 연동 가능`
- 좋은 예: `결정 필요: 비로그인 찜 목록의 보관 기간 — 9월 20일까지 기획 확정`
- 피해야 할 예: `디자인 필요`

## 복사해서 사용하는 템플릿

```md
# [FEATURE] 기능 또는 사용자 결과를 한 문장으로 작성

## 목적

- 해결하려는 문제:
- 기대하는 사용자 또는 비즈니스 결과:

## 사용자 시나리오

- 사용자가 ___한 상태에서 ___하면, ___할 수 있다.
- 예외 상황 ___에서는, ___을 보여 주거나 처리한다.

## 범위

- 포함:
  -
- 제외:
  -

## 완료 조건

- [ ] 사용자가 ___할 수 있다.
- [ ] ___ 상황에서도 예상한 결과 또는 안내를 제공한다.
- [ ] 관련 단위 또는 통합 테스트를 통과한다.
- [ ] 코드 리뷰와 필요한 문서 갱신을 완료한다.

## 작업 현황

- [ ] #000 [BE] API, 데이터 모델 또는 권한 처리
- [ ] #000 [FE] 화면, 상태 관리 및 사용자 흐름 구현
- [ ] #000 [QA] 정상 및 예외 시나리오 검증
- [ ] #000 [DOC] API 명세, 운영 안내 또는 릴리스 노트 갱신

## 의존성 및 블로커

- 선행 이슈:
- 외부 의존성:
- 결정이 필요한 사항:

## 참고 자료

- 디자인:
- 기획 문서:
- API 또는 기술 문서:
```

## 부모 이슈를 닫기 전 확인

- [ ] 모든 하위 이슈가 완료되었거나 제외 사유가 기록되었다.
- [ ] 완료 조건을 실제 사용자 흐름으로 확인했다.
- [ ] 관련 PR, 테스트 결과, 배포 또는 문서 링크가 남아 있다.
- [ ] 이번 범위에서 제외한 요구는 별도 후속 이슈로 등록했다.
