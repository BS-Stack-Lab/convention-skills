# 개발 전 작업 이슈 작성

기능, 개선, 리팩터링을 개발하기 전에 백엔드·프론트엔드 기능 부모 이슈와 하위 테스크 이슈를 작성·수정·검토할 때 사용한다. 이미 발생한 장애·버그·사용자 문의 대응 이슈에는 `team-incident-issue-authoring`을 사용한다.

작성 전에 [개발 전 작업 이슈 원문 가이드](references/development-work-issue-guide.md) 전체와 [기능·테스크 이슈 구조 가이드](references/feature-task-issue-structure-guide.md)를 읽는다. 원문 가이드는 팀이 제공한 내용을 원문 그대로 보관한 기준 문서다.

- 구현 방법보다 사용자 또는 비즈니스 문제와 기대 결과를 먼저 작성한다.
- 기능 부모와 하위 테스크의 제목은 `team-work-item-title-conventions`의 명사형 제목 규칙을 적용한다.
- 알 수 없는 정보는 추정해 채우지 말고 `결정 필요`와 담당자 또는 논의 채널을 남긴다.
- `[BE][FEATURE]`와 `[FE][FEATURE]`는 각각 분리된 부모다. 양쪽에 영향이 있으면 공통 부모 하나를 만들지 않고 두 기능 부모를 관련 이슈로 연결한다.
- 기능 부모에는 목적·범위·완료 조건과 테스크 분리 판단을 작성한다. 독립 배정 가능한 API·화면·테스트·문서 작업만 같은 영역의 하위 테스크로 나눈다.
- 사용자가 백엔드 또는 프론트엔드를 지정하지 않으면 `[BE][FEATURE]`와 `[FE][FEATURE]` 초안을 모두 작성한다. 요청·설계 문서·저장소 구조에서 양쪽 영역이 확인된 경우에도 둘 다 작성한다.
- 백엔드 테스크에는 `team-backend-feature-task-issue-authoring`, 프론트엔드 테스크에는 `team-frontend-feature-task-issue-authoring`을 적용한다. 이슈 초안만 작성할 때도 두 스킬의 템플릿과 분리 기준을 따른다.
- 완료 조건에는 정상 흐름, 예외 흐름, 테스트 또는 리뷰 기준을 포함한다.
- GitHub 이슈 생성·수정처럼 외부 상태를 바꾸는 행동은 사용자가 명시적으로 요청한 경우에만 수행한다.

작성 결과는 원문의 복사 템플릿을 기준으로 하되, 사용자가 제공하지 않은 이슈 번호·담당자·일정·링크는 만들지 않는다.
