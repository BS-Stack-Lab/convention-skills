# 실제 이슈 대응 작성

이미 발생한 버그, 장애, 사용자 문의의 접수·대응·종료 이슈를 작성·수정·검토할 때 사용한다. 개발 전 기능·개선 작업의 부모 이슈에는 `team-development-issue-authoring`을 사용한다.

작성 전에 [실제 이슈 발생 대응 원문 가이드](references/incident-response-issue-guide.md) 전체를 읽는다. 이 파일은 팀이 제공한 내용을 원문 그대로 보관한 기준 문서다.

- 원인이 확실하지 않아도 사용자 영향이 있으면 먼저 사실 기반으로 이슈를 작성한다.
- 장애·버그 이슈의 제목은 `team-work-item-title-conventions`의 명사형 제목 규칙을 적용한다.
- 확인하지 못한 수치나 원인을 추정하지 않고 `확인 중`으로 표시한다.
- P0·P1은 영향·발생 시각·현재 상태·담당자·소통 채널·타임라인을 우선 기록한다. 실제 알림이나 외부 소통은 사용자의 별도 요청 없이는 수행하지 않는다.
- 임시 완화 조치와 근본 해결, 직접 원인과 근본 원인을 분리해 기록한다.
- 비밀번호, 토큰, 개인정보, 결제 정보는 이슈에 남기지 않는다. 로그와 캡처는 마스킹하거나 안전한 내부 링크로 대체한다.
- GitHub 이슈 생성·수정, 담당자 지정, 알림·롤백처럼 외부 상태를 바꾸는 행동은 사용자가 명시적으로 요청한 경우에만 수행한다.

작성 결과는 원문의 복사 템플릿을 기준으로 하되, 사용자가 제공하지 않은 시각·우선순위·이슈 번호·근거 링크는 만들지 않는다.
