# 실제 이슈 발생 대응 가이드

장애, 버그, 사용자 문의처럼 이미 발생한 문제를 접수하고 해결 과정과 재발 방지 조치를 기록하기 위한 이슈 양식입니다. 원인이 확실하지 않아도 사용자 영향이 있으면 먼저 이슈를 생성합니다.

## 이슈 생성 직후 할 일

1. 사용자 영향, 발생 시각, 현재 상태를 먼저 기록합니다.
2. P0 또는 P1이면 담당자와 소통 채널을 바로 지정합니다.
3. 로그, 화면 캡처, 재현 절차처럼 확인 가능한 근거를 첨부합니다.
4. 임시 완화 조치와 근본 해결 작업을 분리합니다.
5. 진행 중인 사실을 `타임라인`에 시간순으로 추가합니다.

비밀번호, 액세스 토큰, 개인 정보, 원본 결제 정보는 이슈에 붙이지 않습니다. 필요한 경우 마스킹한 로그나 안전한 내부 저장소 링크만 사용합니다.

## 항목별 작성 방법

### 1. 제목

형식은 `[BUG][우선순위] 영향이 드러나는 문제`를 권장합니다.

- 좋은 예: `[BUG][P1] 결제 완료 후 주문 내역이 생성되지 않음`
- 좋은 예: `[INCIDENT][P0] 운영 API 인증 오류로 로그인 불가`
- 피해야 할 예: `주문 오류`
- 피해야 할 예: `급함`

원인으로 추정되는 기술 이름은 제목에 단정하지 않습니다. 예를 들어 `Redis 오류`보다 사용자 영향인 `로그인 불가`를 먼저 적습니다.

### 2. 요약

이슈를 처음 보는 사람이 30초 안에 상황을 알 수 있게 작성합니다. 무엇이, 언제, 어디에서 발생했는지 적습니다.

- 좋은 예: `9월 17일 14:05부터 운영 웹에서 카드 결제 완료 후 주문 성공 화면으로 이동하지만 주문 내역이 생성되지 않는다.`
- 피해야 할 예: `주문이 안 된다.`

`현재 상태`는 사실에 맞게 갱신합니다. 예: `접수`, `분석 중`, `수정 중`, `검증 중`, `해결`.

### 3. 우선순위와 영향

우선순위는 작성자의 긴급함이 아니라 사용자 영향과 우회 가능성으로 결정합니다.

| 등급 | 판단 기준 | 기본 대응 |
| --- | --- | --- |
| P0 | 핵심 기능 전체 중단, 보안 사고, 데이터 손실 위험 | 즉시 알림, 담당자 지정, 상황 공유 |
| P1 | 다수 사용자의 핵심 흐름 실패 또는 우회가 매우 어려움 | 당일 대응 및 진행 상황 공유 |
| P2 | 일부 사용자 또는 기능 영향, 우회 가능 | 우선순위 반영 후 계획 대응 |
| P3 | 개선 요청 또는 영향이 낮은 문제 | 백로그 등록 후 정기 검토 |

영향에는 아래 정보를 가능한 한 구체적으로 적습니다.

- 영향을 받는 기능 또는 사용자 집단
- 시작 시각과 발생 빈도
- 현재 우회 방법의 유무
- 금액, 주문 수처럼 이미 확인된 정량 정보

확인하지 못한 정보는 추정 수치로 쓰지 말고 `확인 중`으로 표시합니다.

### 4. 재현 정보

다른 팀원도 같은 결과를 확인할 수 있도록 번호 순서로 작성합니다. 계정, 환경, 앱 또는 브라우저 버전을 빠뜨리지 않습니다.

- 좋은 예: `1. Android 15, 앱 2.4.1에서 로그인한다. 2. 상품 A를 장바구니에 넣는다. 3. 카드 결제를 완료한다. 4. 주문 내역에 상품 A가 없다.`
- 피해야 할 예: `결제하면 가끔 안 된다.`

재현되지 않으면 `재현 불가`라고만 쓰지 말고, 시도한 환경·시간·조건과 관찰된 차이를 남깁니다.

### 5. 근거 자료

문제 판단에 필요한 자료만 첨부합니다.

- 오류 메시지와 마스킹된 로그
- 화면 캡처 또는 짧은 재현 영상
- 관련 배포 버전, PR, 변경 이슈 링크
- 모니터링 대시보드 또는 알림 링크

로그에는 요청 ID, 발생 시각, 서비스 이름처럼 추적에 필요한 식별자를 남기되 민감 정보는 제거합니다.

### 6. 즉시 조치 및 작업 현황

체크박스는 실제로 누가 무엇을 하는지 보이는 상태판입니다. 원인 분석, 코드 수정, 검증처럼 별도 PR이나 담당자가 필요한 작업은 하위 이슈로 분리해 링크합니다.

- 임시 조치 예: 기능 플래그 비활성화, 이전 버전 롤백, 우회 안내
- 근본 해결 예: 누락된 트랜잭션 처리 수정, 회귀 테스트 추가, 모니터링 알림 추가

### 7. 타임라인

발견부터 해결까지의 핵심 사실을 시간순으로 기록합니다. 나중에 책임을 추정하는 기록이 아니라, 다음 대응을 빠르게 이해하기 위한 기록입니다.

- 좋은 예: `14:10 - 주문 생성 실패 알림 확인, P1로 분류`
- 좋은 예: `14:28 - 결제 완료 이벤트 소비 지연 확인, 큐 재처리 시작`
- 좋은 예: `15:05 - 재처리 완료, 신규 주문 생성 정상 확인`

### 8. 원인과 재발 방지

`직접 원인`에는 이번 증상을 만든 조건을, `근본 원인`에는 왜 그 조건을 막지 못했는지 적습니다.

- 직접 원인 예: `주문 생성 소비자가 특정 예외에서 메시지를 재시도하지 않고 종료했다.`
- 근본 원인 예: `실패 메시지에 대한 알림과 재시도 테스트가 없었다.`

재발 방지는 "주의한다"가 아니라 담당자와 완료 기준이 있는 후속 이슈로 연결합니다.

## 복사해서 사용하는 템플릿

```md
# [BUG][P1] 사용자 영향이 드러나는 문제를 한 문장으로 작성

## 요약

- 무엇이 발생했는가:
- 발견 시각 및 발견 경로:
- 우선순위: P0 / P1 / P2 / P3
- 현재 상태: 접수 / 분석 중 / 수정 중 / 검증 중 / 해결

## 사용자 및 서비스 영향

- 영향을 받는 사용자 또는 기능:
- 영향 범위와 빈도:
- 시작 또는 종료 시각:
- 우회 방법 유무:
- 확인 중인 정보:

## 재현 정보

1.
2.
3.

- 기대 결과:
- 실제 결과:
- 환경: 운영 / 스테이징 / 로컬, 앱 또는 브라우저 버전:

## 근거 자료

- 오류 메시지 또는 마스킹된 로그:
- 화면 캡처 또는 영상:
- 모니터링 또는 알림 링크:
- 관련 배포, PR, 변경 이슈:

## 즉시 조치 및 작업 현황

- [ ] 영향 범위 확인
- [ ] 담당자 및 소통 채널 지정
- [ ] 임시 완화 조치 시행 또는 우회 안내
- [ ] 원인 분석
- [ ] 수정 PR 및 코드 리뷰
- [ ] 운영 또는 스테이징 검증
- [ ] 사용자 또는 관련 팀에 결과 공유

## 타임라인

- HH:MM - 발견:
- HH:MM - 영향 확인:
- HH:MM - 임시 조치:
- HH:MM - 원인 확인:
- HH:MM - 수정 및 검증:

## 원인과 재발 방지

- 직접 원인:
- 근본 원인:
- 재발 방지 작업: #000

## 종료 기준

- [ ] 사용자 영향이 해소되었다.
- [ ] 수정 사항이 운영 또는 스테이징에서 검증되었다.
- [ ] 재발 방지 또는 후속 이슈가 등록되었다.
- [ ] 관련 사용자와 팀에 결과를 공유했다.
```

## 이슈 종료 전 확인

- [ ] 문제가 재현되지 않거나 사용자 영향이 해소된 근거가 있다.
- [ ] 임시 조치만으로 끝났다면 근본 원인 또는 개선 작업을 후속 이슈로 연결했다.
- [ ] P0 또는 P1 이슈는 타임라인, 영향, 원인, 재발 방지 조치를 모두 남겼다.
- [ ] 민감 정보가 첨부되지 않았는지 확인했다.
