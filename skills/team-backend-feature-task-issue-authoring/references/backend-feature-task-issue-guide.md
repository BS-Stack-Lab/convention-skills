# 백엔드 기능·테스크 이슈 가이드

## 적용 범위

`[BE][FEATURE]`는 백엔드가 제공할 사용자·시스템 결과를 합의하는 부모 이슈다. `[BE][TASK]`는 그 부모의 범위가 독립적으로 배정·구현·리뷰 가능한 작업일 때만 만드는 하위 이슈다. API, 도메인 규칙, 인증·권한, 데이터 모델, 마이그레이션, 외부 연동, 백엔드 테스트·문서가 대상이다.

화면 문구, 컴포넌트 배치, 클라이언트 상태처럼 프론트엔드만의 결과는 이 이슈에 넣지 않고 `[FE][FEATURE]` 또는 `[FE][TASK]`로 분리한다. API 계약 협의와 의존성은 관련된 양쪽 이슈에 명시한다.

## 테스크 이슈를 만들기 전 판정

`[BE][FEATURE]`의 본문에 API·도메인·DB·테스트 항목이 있다고 해서 각각 테스크 이슈를 만들지 않는다. 아래 중 하나 이상이 성립할 때만 `[BE][TASK]`로 분리한다.

- API 계약 변경과 도메인·저장 규칙 변경이 각각 별도 PR, 담당자 또는 배포 순서로 관리되어야 한다.
- Flyway Migration, 데이터 백필, 외부 시스템 연동, 인증·권한, 성능·보안 검증처럼 위험과 완료 조건이 독립적이다.
- 통합·계약·회귀 테스트가 별도 환경, 테스트 데이터, 담당자 또는 일정으로 수행되어 독립 증빙이 필요하다.
- 한 이슈의 변경량이 하나의 PR·리뷰·롤백 단위로 다루기 어렵거나, 선행·후행 의존성이 명확하다.

다음은 분리하지 않고 기능 부모 또는 같은 구현 테스크의 완료 조건으로 남긴다.

- API 구현과 함께 작성하는 단위 테스트, 예외 처리, 간단한 API 문서 갱신
- 같은 담당자가 하나의 PR에서 함께 변경하는 도메인 코드와 Repository 코드
- 기능 요구나 API 계약이 아직 확정되지 않아 독립 결과를 정의할 수 없는 조사 항목

테스트를 별도 테스크로 만들었다면 제목을 `테스트 추가`처럼 쓰지 않는다. 예를 들어 `[BE][TASK] 결제 승인 API의 Sandbox 계약·재시도 통합 검증`처럼 독립 검증 대상, 환경, 완료 결과를 쓴다.

## 작성 기준

- 기능 부모는 백엔드 책임, 포함·제외 범위, API·데이터 영향, 완료 조건, 테스크 분리 판단을 기록한다.
- 하나의 테스크는 하나의 PR로 검토 가능한 변경 묶음이 원칙이다. 독립 배포·롤백 단위가 둘 이상이면 분리한다.
- 테스크는 부모의 목적을 반복하지 않고, 자신이 제공하는 백엔드 결과와 경계를 명확히 한다.
- DB 변경은 적용 방식과 호환성, 마이그레이션 여부를 작성한다. 이미 적용된 Migration을 수정하는 계획은 금지한다.
- API가 변경되면 소비자 영향과 하위 호환성, 오류 처리·문서 반영을 작성한다.
- 비밀번호, 토큰, 개인정보, 내부 URL, 운영 설정은 이슈에 기록하지 않는다.

## 분리 예시

`비로그인 찜 목록 유지` 기능의 백엔드 테스크는 `세션별 찜 목록 조회·저장 API 제공`처럼 작성한다. 이 테스크에는 요청·응답, 인증 전환, 저장 정책, 오류·테스트를 둔다. 찜 버튼 상태·목록 렌더링은 프론트엔드 테스크로 둔다.
